# 規格：跨裝置語音輸入（家庭網路原型）

## Problem Statement

使用者希望以手機麥克風口述內容，將辨識後的繁體中文直接輸入 Windows 電腦目前游標位置，不必在手機上複製、切換裝置，再到電腦貼上。現有專案只有 Android 空殼與範例測試，尚無語音辨識、跨裝置傳輸或 Windows 接收端。

## Solution

使用者在 Android 手機上設定個人 Gemini API key 與 Windows Receiver 的位址、埠和配對碼。Windows 執行輕量 Python Receiver。兩者位於可互通的家庭區網時，使用者按住手機上的說話鍵，放開後等待 Gemini 3.5 Transcribe Live 產生**轉錄定稿**；手機確保中文字形為繁體，再送至已驗證的 Receiver。Receiver 將文字寫入剪貼簿並對當下焦點模擬 Ctrl+V。手機顯示**輸入就緒**燈號及最近一段文字；失敗顯示原因，不自動補貼。

## User Stories

1. 身為使用者，我想在自己的 Android 手機上啟動語音輸入畫面，以便把手機當作電腦輸入工具。
2. 身為使用者，我想在手機上手動設定 Gemini API key，以便使用自己的辨識服務額度。
3. 身為使用者，我想在手機上手動設定 Windows 的 IP、埠和配對碼，以便連接指定的電腦。
4. 身為使用者，我想由 Windows Receiver 看到應輸入的位址、埠和配對碼，以便完成首次連線。
5. 身為使用者，我想手機只在已驗證連線且具備辨識啟動條件時顯示輸入就緒，以便知道何時可以嘗試口述。
6. 身為使用者，我想在手機左上角看到單一連線狀態燈與文字說明，以便分辨就緒和已知故障。
7. 身為使用者，我想按住說話、放開結束此次口述，以便控制收音範圍。
8. 身為使用者，我想手機在首次錄音時請求必要權限，以便明白麥克風何時被使用。
9. 身為使用者，我想在麥克風權限被拒絕時看到錯誤而不是假裝已收音，以便修復設定。
10. 身為使用者，我想只在按下說話時連接 Gemini Live，以便避免閒置時維持串流連線。
11. 身為使用者，我想可在手機上看到辨識中的文字或狀態，以便知道說話是否被接收。
12. 身為使用者，我想只有轉錄定稿被送至電腦，以便模型修改暫定稿時不會重複貼上。
13. 身為使用者，我想口語贅字與口誤由 SMART 模式適度整理，以便貼上的內容更適合閱讀。
14. 身為使用者，我想中文輸出是繁體字形，以便在台灣中文情境中使用。
15. 身為使用者，我想中文和英文混合口述仍保留可讀的英文字母與標點，以便輸入日常內容。
16. 身為使用者，我想放開說話後每段定稿最多觸發一次貼上，以便避免內容重複。
17. 身為使用者，我想 Receiver 只接受有正確配對碼的手機，以便其他未授權的區網裝置無法觸發貼上。
18. 身為使用者，我想在 Windows 記事本或一般瀏覽器輸入框中直接看到口述文字，以便不用手動複製貼上。
19. 身為使用者，我想文字貼到接收瞬間的目前焦點，以便切換視窗後能輸入到我正在編輯的位置。
20. 身為使用者，我想貼上時不自動補空格或換行，以便避免意外送出聊天訊息或執行命令。
21. 身為使用者，我接受原剪貼簿被定稿覆蓋，以便 Receiver 保持簡單，並可在需要時再貼同一段文字。
22. 身為使用者，我想辨識、驗證或傳送失敗時有明確狀態提示，以便知道這段話可能沒有輸入電腦。
23. 身為使用者，我想失敗的文字不在重連後自動補貼，以便避免延遲貼錯視窗。
24. 身為使用者，我想手機畫面暫留最近一段文字並可手動複製，以便貼上失敗或貼錯位置時仍能自行處理。
25. 身為使用者，我想退出 App 後不保存逐字稿歷史，以便減少敏感內容留存。
26. 身為使用者，我想手機與 Receiver 可在斷線或設定變更後重新建立已驗證連線，以便繼續新的口述而不補貼舊內容。
27. 身為使用者，我想過長或不符合協定的輸入被 Receiver 拒絕，以便降低意外或惡意貼上風險。
28. 身為後續開發者，我想語音辨識與跨裝置傳送分離，以便將來替換辨識服務或傳輸方式。
29. 身為後續開發者，我想 Windows 的接收與貼上分離，以便用可觀察結果測試協定，而不在單元測試中操作真正視窗。
30. 身為後續開發者，我想未來能在不改寫口述與貼上流程的前提下增加藍牙傳輸，以便依環境選擇連線方式。

## Implementation Decisions

- 第一版只驗收 SM-F7410（Android API 36），使用現有 Android 專案作為起點；另建立 Windows Python Receiver。沒有現成應用邏輯可沿用。
- 採按住收音、放開結束一次輸入；前台操作，不做背景常駐收音。辨識使用 Gemini 3.5 Transcribe Live 的 SMART 模式，將「暫定辨識」與「轉錄定稿」區分；只有後者可被送出，空結果不貼上。若 Live 服務未及時回定稿，需顯示等待或錯誤，不以暫定稿代替。
- 中文輸出必須為繁體字形；需要時在送出前轉字，不要求轉成台灣在地詞彙。中英混用不得把英文當作繁簡字轉換目標。實際字形品質需在實機驗收。
- 個人 API key 由手機使用者設定並保存在裝置上；不得硬編進 APK、提交至 Git 或列入日誌。Receiver 不持有 Gemini key、不代理音訊。Gemini Live 連線只在按下時建立；閒置就緒僅表示必要條件具備，並非 Gemini 已連線。
- 採可替換的傳輸邊界：Android 的輸入流程只委託傳送轉錄定稿與回報連線狀態，Windows 的接收流程只交付已驗證定稿給貼上動作；兩端首個具體傳輸都是 WebSocket。藍牙僅預留新增實作的邊界，第一版不實作藍牙或切換 UI。配對驗證、訊息界線與失敗回報不得與畫面／剪貼簿程式碼混雜。
- 同一可互通家庭 LAN；使用者手動輸入 Receiver IP、埠、配對碼。Receiver 拒絕未驗證、無效或超限訊息。以 `ws://` 運作的配對碼只是授權檢查，**不是傳輸加密**；區網可能遭竊聽。辦公室使用前必須另做加密與部署安全處理。
- Receiver 收到合格定稿後寫入 Windows 剪貼簿，再模擬 Ctrl+V 至當時焦點；不還原剪貼簿，不額外送空格或換行。輸入失敗不自動重試，手機保留最近一段在畫面中供手動複製；不持久化逐字稿。無法保證所有 Windows 控制項都能貼上，也無法保證遠端回覆等於目標應用已顯示文字。
- 左上角單燈僅在已驗證的 Windows 連線與 Gemini 必要啟動條件同時成立時表示輸入就緒；其他狀態用非綠燈與文字解釋。按下後 Gemini 連線失敗時即更新狀態，不報假成功。
- 以「一次口述／一段轉錄定稿／至多一次貼上」作為行為契約；不設計斷線佇列或自動重送。網路結果不明時不得偷偷再次貼入。

## Testing Decisions

- 以使用者可觀察結果寫測試：是否貼一次、是否出現正確繁體文字、失敗時是否沒有貼上及是否顯示對應狀態；不以具體類別名稱、內部呼叫次數或模擬網路的實作方式當作需求本身。
- 主要自動測試邊界：手機產生轉錄定稿 → 經傳輸 → Receiver 接收並觸發貼上。用可控辨識輸出代替付費 Gemini，使用可觀察貼上動作代替真正鍵盤注入，覆蓋暫定稿不貼、定稿只貼一次、空定稿不貼、斷線不補貼、未驗證與超限訊息不貼、繁體字形與中英混用。
- 對辨識狀態／按住放開／權限失敗與輸入就緒燈號做 Android 行為測試；對驗證、訊息接收、剪貼簿貼上決策做 Python 自動測試。通道整合測試要能在本機驗證兩端共用的協定行為。
- 真實驗收須在 SM-F7410 實機與 Windows Receiver 上執行，測試短句、中英混用、SMART 口誤、中文繁體、記事本與瀏覽器輸入框、焦點切換、斷網與錯誤配對碼。檢查不添加換行或空格，並驗證原剪貼簿被覆蓋。
- 現有 Android 測試僅為範例算術與 package name 測試，沒有可借用的領域測試或整合測試先例；新增測試應先鎖定高層行為，而不是沿用範例空測試。

## Out of Scope

- BluetoothTransport 的實作、跨網路連線、局域網自動探索、QR 配對、多裝置。
- 辨識暫定稿貼上／回刪、長時間背景錄音、離線 STT、逐字稿持久歷史、斷線自動補貼、剪貼簿原樣還原。
- 辦公室或公共 Wi-Fi 正式部署、WSS/TLS 憑證信任流程、終端機／管理員權限視窗／任意應用的可靠貼上保證。
- 在 Windows 端代理 Gemini 或分發短效憑證、多使用者金鑰管理、進階詞彙級台灣在地化。

## Further Notes

- 本規格基於已確認的原型範圍（`docs/prototype-scope.md`）及專案詞彙（`CONTEXT.md`）。Gemini 3.5 Transcribe Live 與非直播音檔轉錄是不同端點；前者提供暫定稿與定稿、單次串流有時長限制，應在實機驗證收尾與延遲：[Google Live transcription 文件](https://ai.google.dev/gemini-api/docs/live-api/live-transcribe)。
- 原型安全限制必須在操作說明中明確標示：不可因有配對碼就誤認 `ws://` 適合辦公室或敏感資訊。
- 建議後續按可運作的垂直切片拆票，先驗證 Receiver 與定稿協定，再接實機錄音及 Gemini，最後補字形轉換、錯誤狀態及端到端驗收。
